Every cluster setting#

Use this section to find a setting’s name, default and effect. All site settings live in the project’s config/config.yaml, under execution, never in the copied workflow: an edit under workflow/ changes the recorded workflow digest and the project then refuses to run. Set them with bulkseq config set -C PATH execution.<setting> <value>, or in the desktop interface under Analysis setup, Compute resources, Cluster (Slurm) settings. A value that starts with --, such as --mail-type=FAIL, needs -- in front of it so the command does not read it as an option. A structured value (a list or a mapping) is given as YAML or JSON in quotes. In the desktop interface, Save Cluster Settings checks these settings and the per-step table and writes them to the project; Copy Cluster Commands copies the login-node commands that check and run the project (bulkseq check, a dry run, bulkseq run --exec-profile slurm and bulkseq slurm-script --submit).

Note

A change that only affects scheduling (anything under execution, resources, rule_threads, rule_memory_gb or rule_runtime_min) keeps the configuration file’s timestamp, so Snakemake does not plan finished steps again, and a changed thread count, memory or walltime reruns nothing. The one exception is rule_memory_gb.star_index at 35 GB or more, which changes the STAR command (see Large genomes) and rebuilds the index and every alignment once.

Check

bulkseq config show -C PATH --section execution prints the values the project now holds.

bulkseq config set -C PATH execution.slurm_partition PARTITION
bulkseq config set -C PATH execution.slurm_account myproject
bulkseq config set -C PATH execution.slurm_extra -- --mail-type=FAIL
bulkseq config set -C PATH execution.rule_resources '{"star_align": {"slurm_partition": "bigmem"}}'
bulkseq config show -C PATH --section execution

Per-step threads, memory, walltime and placement#

Use this section to size one step or send it to another partition. Each heavy step declares its own threads, memory and walltime; every executor reads them. Change one with bulkseq config set -C PATH rule_memory_gb.star_index 160, rule_threads.star_align 16 or rule_runtime_min.star_index 1440. A step without a walltime gets execution.default_runtime_min; one without memory gets the larger of execution.default_mem_mb and twice its input size. To send one step to another partition, QOS or node type, set execution.rule_resources.<step>.<field> with field slurm_partition, slurm_account, qos, constraint, clusters or slurm_extra. Some step keys cover several workflow rules, so one setting sizes all of them: fastqc (raw and trimmed reports), fastp (also the Trim Galore and Trimmomatic rules, single-end and paired-end), sortmerna (also its index and the RiboDetector rules) and deseq2 (also the limma, voom and edgeR differential-expression rules).

Caution

Save Resources in the desktop interface resets per-step threads and memory to the computer it runs on. Set the cluster values afterwards, in the Cluster (Slurm) settings table or with bulkseq config set.

Check

A retried job asks for the attempt number times its walltime, and times its memory when execution.max_mem_mb is set. Set max_runtime_min and max_mem_mb to the partition’s limits so a retry stays schedulable.

Large genomes#

Use this section when the genome is larger than a typical mammalian one. Maize (about 2.2 Gb) and bread wheat (about 14.5 Gb) need far more than the defaults. On the bundled reference catalogue, STAR’s index build for maize peaked at 57.9 GB on the reference PC; wheat could not be indexed in 64 GB. The STAR manual asks for at least 32 GB for the 3.1 Gb human genome, roughly 10 bytes per base, which suggests on the order of 150 GB for wheat; treat that as an estimate to confirm on a first run, not a measurement. BulkSeq passes STAR a genome-generation limit of 90% of rule_memory_gb.star_index whenever that is above STAR’s 31 GB default, that is from 35 GB, so raising the memory is enough. Because the flag changes the STAR command, a project that already holds an index built with 35 GB or more rebuilds it once after this release. Aligning to a wheat STAR index also holds the whole index in memory, one alignment at a time per node; Salmon and HISAT2 need much less. Bread wheat and barley chromosomes exceed the 229−1 bp (about 537 Mb) a BAI index can address, so their BAMs are indexed as CSI automatically; another genome with such a sequence needs reference.bam_index csi, and the reference check stops the run with that instruction before alignment.

GenomeSuggested settingBasis
Maize, STARrule_memory_gb.star_index 72, star_align 40Index peak measured at 57.9 GB on the reference PC under STAR’s default limit; 72 GB gives STAR a 64.8 GB limit with headroom. Alignment is estimated from the index size
Wheat, STARrule_memory_gb.star_index 200, star_align 180, walltimes of a day or moreEstimated from the STAR manual’s human figure; not measured
Wheat, SalmonDefaults, with more walltime for salmon_indexThe route the benchmark plan uses for wheat on one PC

Caution

Plan disk for the index too. A STAR index occupies several times the genome size on disk, with more while it is built; for wheat that is on the order of a hundred GB or more (an estimate). Check the quota first.

Run stages#

Use stages when only part of a run can happen on a given host, for example downloads on the login node and computation elsewhere. --stage prefetch runs only the downloads. --stage compute runs everything except the online analysis steps (enrichment, annotation transfer, STRING and MSigDB) and what depends on them: their figures, the check summary and the reports. --stage online runs only those online steps. --stage all, or no --stage, does whatever is still missing. A staged run uses the local executor, so give --stage only with the default --exec-profile local; with another profile the command stops with an error. --cores and --memory-gb size a local run for one launch without changing the project. Inside the single-allocation job the stage is the script’s first argument: sbatch config/slurm_allocation.sbatch all runs every step, including the online ones.

bulkseq run -C PATH --stage prefetch --cores 2
bulkseq run -C PATH --stage compute --cores 128 --memory-gb 240
bulkseq run -C PATH --stage online --cores 2
bulkseq run -C PATH --cores 2

Follow, inspect and control a run#

Use this section while a run is in progress or after it ended. Every job BulkSeq submits is an ordinary Slurm job, so the site’s own commands work on it. Per-step jobs are named by the run’s identifier and carry the step name in their comment; the one-allocation job is named bulkseq-<project>.

Note

BulkSeq keeps every scheduler log. A cluster, split-stage or in-allocation run also mirrors its own output into logs/bulkseq_run_<time>_<profile>_<stage>.log, so the record survives a closed terminal.

Disconnects, stopping and resuming#

Use this section after a dropped connection, an interruption or a failed job. Closing the terminal, a dropped SSH session or kill stops a per-step run the same way Ctrl-C does: Snakemake cancels the jobs it submitted, so none is left running unattended. To survive a disconnect, run inside tmux or screen, or use one allocation. Resume with --mode resume, which unlocks the project and repeats incomplete steps. A failed job is submitted again execution.retries times with more walltime; a genuine tool error fails again and stops that branch while independent steps continue.

Check

Before resuming, BulkSeq warns when you still have jobs in the queue. Cancel any that belong to the stopped run with scancel, or two jobs would write the same files.

Note

Updating BulkSeq part-way through a study re-synchronises the project’s workflow on its next run. Pin one release for a whole benchmark and record it.

bulkseq run -C PATH --exec-profile slurm --mode resume

The exit status is that of a local run: 0 on success, 2 for a usage error, 3 when the project, its configuration or this host cannot be used, 5 when the workflow fails and 130 when interrupted. Exit codes and statuses lists each with what to do next.

Kubernetes#

The kubernetes profile is a starting point, not a supported route. Its executor plugin is not part of the environment, and every pod would need a container image carrying the full tool stack. bulkseq run --exec-profile kubernetes exits 3 while the plugin is missing; it cannot detect a missing image. Read workflow/profiles/site/kubernetes/config.yaml before attempting it.

What has been verified#

Use this section to see what the cluster support has and has not been tested against. Both modes were run on a single-node Slurm 23.11 test cluster with job accounting, under WSL2 (Ubuntu 24.04), on a synthetic 3-versus-3 paired-end project. Per-step mode submitted 53 jobs, all of which completed; sacct shows the configured partition, account, QOS, job-name prefix and the two-CPU minimum on every job, and the step placed through rule_resources carried its extra option. Single-allocation mode ran the whole offline part of the same project in one job and a login-node run finished the remainder; a script submitted from another directory logged into the project, a job stopped part-way resumed when submitted again, and the online stage followed by a job submitted with all finished a project. The count matrix and the DESeq2 table of the local, per-step and single-allocation runs are byte-identical. A hangup signal to a per-step run cancelled its 14 queued jobs. A project finished under 0.36.0, upgraded, saved by the interface and given new scheduling settings had nothing to rerun. The revised lock installed in that environment, changing only the two header packages, and solves in a dry run for glibc 2.28, 2.34 and 2.39. CSI indexing under the .bai name was checked with samtools 1.22.1 and pysam on a 600 Mb synthetic sequence. In 0.36.0 the same test cluster ran synthetic FASTQ and count-matrix projects in 54 and 16 jobs with results identical to local runs. No production cluster has been used. The Apptainer image is built and self-tested by the Environment CI workflow only, never run under a cluster’s Apptainer. Kubernetes execution has not been tested.

Check

Before a full study, run a small project under your site’s policy and confirm in sacct and logs/slurm/ that its jobs reached the scheduler and completed.
